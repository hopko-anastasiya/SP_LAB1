## Опис завдання
Мета роботи — дослідити продуктивність програми множення матриць, виявити її вузькі місця за допомогою низькорівневих інструментів Linux (`perf`, `time`, FlameGraph) та провести оптимізацію.

* **Задача:** Множення двох матриць $A$ і $B$ розміром $1200 \times 1200$ елементів типу `float`.
* **Пам'ять під дані:** Кожна матриця займає $\approx 5.76\text{ МБ}$, сумарно під три матриці потрібно $\approx 17.3\text{ МБ}$.
* **Контрольна сума:** Для перевірки правильності обчислень виводиться перший елемент матриці результату — $C[0][0] = 575.280151$ (в обох варіантах значення збіглося абсолютно точно).

## 1. Побудова та аналіз FlameGraph

### Процес зняття профілю та генерації графіків
Для запису стеку викликів використовувався профайлер `perf record` разом із набором скриптів Brendan Gregg:

```bash
# 1. Запис профілю повільної версії (570 семплів, частота 99 Гц)
perf record --no-buildid-mmap -e task-clock -F 99 -g -- ./prog_slow
perf script | ./FlameGraph/stackcollapse-perf.pl | ./FlameGraph/flamegraph.pl > results/flamegraphs/flamegraph_slow.svg

# 2. Запис профілю швидкої версії (181 семпл, частота 999 Гц через малий час виконання)
perf record --no-buildid-mmap -e task-clock -F 999 -g -- ./prog_fast
perf script | ./FlameGraph/stackcollapse-perf.pl | ./FlameGraph/flamegraph.pl > results/flamegraphs/flamegraph_fast.svg
```

### Інтерпретація отриманих результатів FlameGraph

1. **Базова версія:**
   * Графік являє собою практично одну суцільну смугу на всю ширину екрана.
   * Звіт `perf_report_slow.txt` підтверджує: функція `multiply_matrices` забирає **99.47%** усіх зафіксованих тактів процесора.
   * memory-bound вузького місця: процесор майже весь час простоював в очікуванні завантаження даних із RAM.
2. **Оптимізована версія**
   * На графіку оптимізованої версії функція множення виконується настільки швидко, що стали помітними інші фази життєвого циклу програми.
   * За звітом `perf_report_fast.txt` з'явилися стеки викликів функції `init_matrices` (2.21%) та бібліотечної ініціалізації `__memset_avx2_unaligned_erms` (1.10%), а також робота системних викликів сторінкового менеджера ядра.

Отже, було використано аналітичну розрахункову модель енергоспоживання $E = P \times t$ на базі типових параметрів процесора:
* Потужність платформи в простої: $P_{\text{idle}} = 12\text{ Вт}$.
* Потужність активного обчислювального блоку під навантаженням: $P_{\text{load}} = 42\text{ Вт}$.
* Динамічна надбавка для процесу програми: $\Delta P = P_{\text{load}} - P_{\text{idle}} = 30\text{ Вт}$.

## 4. Порівняння програми до та після оптимізації 

### Суть оптимізації та порядок обходу масивів
1. **Проблема базової версії (`src/matrix.c`):**
   Використовувався порядок циклів `i -> j -> k`:
   ```c
   for (int i = 0; i < N; i++)
       for (int j = 0; j < N; j++)
           for (int k = 0; k < N; k++)
               C[i][j] += A[i][k] * B[k][j];
   ```
   У мові C двовимірні масиви зберігаються в пам'яті по рядках (Row-major order). При зміні індексу `k` матриця `B[k][j]` зчитується по стовпчиках з кроком у цілий рядок ($1200 \times 4 = 4800\text{ байтів}$). Це призводить до вимивання кеш-ліній (cache thrashing) та постійних промахів кешу L1/L2.

2. **Рішення в оптимізованій версії (`src/matrix_opt.c`):**
   Порядок циклів змінено на `i -> k -> j`:
   ```c
   for (int i = 0; i < N; i++) {
       for (int k = 0; k < N; k++) {
           float r = A[i][k];
           for (int j = 0; j < N; j++) {
               C[i][j] += r * B[k][j];
           }
       }
   }
   ```
   У внутрішньому циклі змінюється індекс `j`. Тепер елементи масивів `B` і `C` обходяться послідовно по пам'яті (крок 4 байти, stride-1). Процесор завантажує всю 64-байтну лінійку кешу й використовує її повністю (просторова локальність).

### Різниця в асемблерному коді та AVX2 SIMD

Порівняння файлів `asm_slow.txt` та `asm_fast.txt` демонструє різницю у згенерованих машинних інструкціях:

#### Базовий код (`prog_slow`):
Працює за класичною скалярною схемою x86-64:
```assembly
movss  (%rdx,%rax,1),%xmm0   # Завантаження 1 числа float у 128-бітний регістр xmm
mulss  %xmm2,%xmm0           # Скалярне множення двох чисел float
addss  %xmm1,%xmm0           # Скалярне додавання
movss  %xmm0,(%rdx,%rax,1)   # Запис одного результату назад у пам'ять
```
Кожна математична операція обробляє лише одне 32-бітне число.

#### Оптимізований код (`prog_fast` з прапорцями `-O3 -mavx2`):
Послідовний доступ до пам'яті дозволив компілятору згенерувати векторні команди розширення **AVX2**:
```assembly
vbroadcastss (%rdi),%ymm3                 # Дублювання значення r = A[i][k] у всі 8 слотів 256-бітного ymm3
vmulps       (%rcx,%rax,1),%ymm3,%ymm0    # Одночасне множення 8 чисел float за один такт!
vaddps       (%rdx,%rax,1),%ymm0,%ymm0    # Одночасне додавання 8 чисел float
vmovaps      %ymm0,(%rdx,%rax,1)          # Запис 256 бітів (8 float) вирівняним блоком у пам'ять
```
* Використовуються 256-бітні векторні регістри `%ymm0`–`%ymm5`.
* Замість поодиноких `mulss` компілятор викликає `vmulps`, що обробляє 8 значень паралельно за одну команду.

### Підсумок
Поєднання правильного порядку обходу пам'яті та автоматичної SIMD-векторизації процесора дало:
* Скорочення реального часу виконання: **з 5.43 с до 0.23 с (speedup 23.7×)**.
* Скорочення процесорного навантаження (`task-clock`): **з 5584 мс до 151 мс (36.8×)**.
* Зниження сумарних витрат електроенергії системи: **у ~24 рази**.
